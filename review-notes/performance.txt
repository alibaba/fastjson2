Performance/codeSize review (finalreactor2 main compile, JDK 25, compiled classfile Code attribute lengths; no benchmark or throughput claims).
Thresholds requested by AGENTS.md: 35 bytes (C1 MaxInlineSize), 325 bytes (C2 FreqInlineSize). Size is only an inlining eligibility constraint; call-site profiles, compiler policy and other limits still apply. Values below are post-change sizes, not baseline deltas.

JSONReader numeric conversions: getInt32Value 486, getInt64Value 372, getBigDecimal 787 (all above 325); readBigInteger 9 (below35), getBigInteger 46 (below325). Exact decimal exponent scaling stays in BigDecimal arithmetic instead of lossy String/double round-tripping. Magnitude checks add no allocation to primitive fast paths. Final getDoubleValue is322 bytes after consolidating high-word checks and sharing its fallback (previous intermediate build334); it now fits325. JSONReaderUTF8.readBoolValue is325 bytes after resetting wasNull, exactly at the requested C2 threshold.

Small writer methods: UTF8/UTF16 writeString(boolean)14/14, writeQuote10/44, writeInt8 scalar101/102, byte-array173/174, writeInt16104/102, writeInt32102/100, writeInt64152/150, float142/152, double145/155, UUID316/292. Thus boolean wrappers and UTF8 quote remain below35; the other listed methods remain below325. Capacity-bound changes are integer arithmetic plus existing rare grow() allocation; slice bounds avoid reading/encoding adjacent backing-buffer content. UTF16 escaped-slice writer is724 bytes, above325; its added growth checks execute only when emitting six-character Unicode escapes. UTF8 raw UTF8 encoding delegates to the existing encoder, with no intermediate String allocation.

ObjectReaderProvider.getObjectReader(long):178 bytes, below325. Correct provider/classloader isolation adds a volatile cache read and context-classloader lookup/comparison on cache hits. Hash cache hits still return without boxing/allocation; misses retain existing Long boxing/map lookup and occasional cache-pair allocation. Cache invalidation is off the repeated lookup path.

TypeUtils.parseDouble(byte[]/char[]):660 bytes each; parseFloat(byte[]/char[]):659 each, above325. Added exponent-end/suffix checks do not allocate on valid fast paths. Existing String/JDK-parser fallback remains for unsupported or malformed number forms; no new general-purpose allocation fallback was introduced for ordinary valid decimal input.

JSONReaderJSONB hashes: readFieldNameHashCode560, readTypeHashCode293, readTypeHashCode0() 889, readValueHashCode222, getNameHashCode50, getNameHashCodeLCase439. Type/value/simple-name methods fit325; field/lowercase/slow-type methods remain above325. ASCII hashing stays byte-based. Material tradeoff: UTF8/UTF16 wire strings now call getString() then Fnv, producing decoded String/backing storage for Unicode field/value hashes; this can matter for non-ASCII-heavy workloads. This is a deliberate correctness fallback (encoding-independent UTF16/Fnv semantics), not demonstrated performance equivalence. Profiling should guide a future allocation-free decoder/hash implementation.

Other fallbacks: escaped Latin1 getString delegates to the ASCII reader's decoder, still allocating only the requested decoded string. ASM root/schema readers and constructor NullOnError parameters now use existing reflective/adaptor paths; ordinary unconfigured generated readers retain generation. These are configuration-specific fallbacks, not an added general hot-path allocation.
